§1 — The Baseline: Classic 5-Stage Pipeline

Every computer architecture course teaches the canonical RISC pipeline. It's simple, elegant, and painfully sequential.

// Classic 5-stage in-order pipeline
┌───────┐  ┌────────┐  ┌─────────┐  ┌─────────┐  ┌──────────┐
│Fetch  │→ │Decode  │→ │Execute  │→ │Memory   │→ │Writeback │
│(IF)   │  │(ID)    │  │(EX)     │  │(MEM)    │  │(WB)      │
└───────┘  └────────┘  └─────────┘  └─────────┘  └──────────┘
    ↑                                                    ↓
    └──────────────── Branch Target ────────────────────┘

The Fundamental Problem: Instructions execute in strict program order. If instruction N stalls (cache miss, data hazard, slow multiply), everything behind it stalls too. A single 10-cycle multiply creates 9 cycles of bubbles. Pipeline efficiency collapses.

Example: String Copy Loop (In-Order)

loop:
    LDR  X4, [X3, #0]   ; Load takes 2 cycles
    STR  X4, [X5, #0]   ; Stalls until LDR completes
    ADDI X3, X3, #4     ; Stalls behind STR
    ADDI X5, X5, #4     ; Stalls behind ADDI
    SUBI X6, X6, #1     ; Stalls behind ADDI
    CBNZ X6, loop       ; Stalls behind SUBI

// Execution Timeline (Cycles)
// LDR:  IF  ID  EX  M1  M2  WB
// STR:      IF [STALL---] ID  EX  M   WB
// ADDI:         [STALL-------] IF  ID  EX  M   WB
// Throughput: ~12 cycles per iteration

Key Observation: The pointer arithmetic (ADDI X3, X3, #4) is completely independent of the memory operation (LDR X4, [X3, #0]), but the in-order pipeline forces them to execute sequentially. This is wasted parallelism.

§2 — The Out-of-Order Concept

Out-of-order execution asks a simple question: why wait for instructions that aren't ready when other instructions are?

The Three Pillars

Register Renaming
Problem: ADDI X6, X0, #72 followed by ADDI X6, X0, #101 looks like a dependency (both write X6)
Solution: Map each write to a different physical register: X6→p40, then X6→p41
Result: False dependencies (WAW/WAR) disappear. Both execute in parallel.
Dynamic Scheduling
Problem: How does hardware know which instructions are ready?
Solution: Issue Queue tracks operand readiness. Wakes instructions when results broadcast.
Result: Instructions issue as soon as operands ready, not in program order.
Reorder Buffer (ROB)
Problem: If instructions finish out-of-order, how do we handle exceptions correctly?
Solution: Buffer results. Commit to architectural state in program order.
Result: Precise exceptions. Memory writes happen in order. Speculation is safe.
Superscalar (2-Wide)
Problem: Even OOO execution is bottlenecked if we only fetch 1 instruction/cycle
Solution: Fetch, decode, rename, and commit 2 instructions per cycle
Result: Theoretical 2.0 IPC (actual: ~1.7 IPC steady-state)

§3 — Measurable Improvements Over Baseline

Methodology: These metrics compare the final OOO superscalar implementation against a hypothetical 5-stage in-order baseline synthesized for the same FPGA (Arty A7-35T). Actual synthesis comparison will be performed to validate these estimates.

Metric Baseline (5-Stage) OOO Superscalar Improvement
IPC (Average) 0.7 - 0.9 1.5 - 1.7 1.9× throughput
Clock Frequency ~120 MHz ~50 MHz -58% (complexity penalty)
Effective Performance 84-108 MIPS 75-85 MIPS ~0.9× (lower clock hurts)
Branch Penalty 3 cycles (fixed) 1-4 cycles (predicted) 2× better on average
Load Latency Hiding None (full stall) Executes independent ops 3-5 cycles saved per load
Resource Utilization ~3,000 LUTs ~18,000 LUTs 6× larger (OOO overhead)

Reality Check: The OOO design sacrifices clock frequency for higher IPC. On the Arty A7 FPGA, the complex combinational paths (CDB arbitration, wakeup logic) fail timing at 100 MHz. The design runs at ~50 MHz but sustains higher IPC, resulting in comparable effective performance with better latency tolerance.

Where OOO Wins

  • Memory-heavy code: Loads execute early while ALU ops fill bubbles (up to 2.5× speedup)
  • Independent operations: Pointer arithmetic, loop counters, and data processing overlap perfectly
  • Branch-heavy code: 2-bit predictor + BTB reduces mispredicts from 100% to ~20%

Where Baseline Competes

  • Straight-line ALU code: Simple adds/shifts benefit from higher clock (1.4× faster)
  • Multiply-accumulate loops: Serialized by true dependencies, OOO can't parallelize
  • FPGA resource constraints: 6× smaller means more complex SoC fits alongside baseline

Bug #1: Free List Always Allocated p32

Register Reuse Corruption
8 hours wasted
Symptom
p32 allocated to X6 three times in 20 cycles. String characters corrupted — 'H' became 'e', 'l' became garbage.
Root Cause
// WRONG (old code):
for (int i = 0; i < 32; i++) {
    if (free_mask[32+i]) {
        alloc_phys = 32 + i;
        break;  // ← Always picks LOWEST free register!
    }
}
Always searched from p32 upward, always picked first available. After p32 committed and freed, it immediately became "first available" again → immediate reuse → corruption.
Fix
// CORRECT (round-robin):
logic [5:0] alloc_ptr;  // Rotating pointer

for (int i = 0; i < 32; i++) {
    int idx = 32 + ((alloc_ptr - 32 + i) % 32);
    if (free_mask[idx]) {
        alloc_phys = idx;
        alloc_ptr = idx + 1;  // Advance for next alloc
        break;
    }
}
Lesson Learned
"First available" algorithms create hot spots. Round-robin spreads allocations evenly, ensuring minimum 32-cycle gap before reuse.

Bug #2: ROB Occupancy Frozen at 1

Multi-Driver Conflict + Hardcoded Value
15 hours wasted
Symptom
[ROB_ALLOC] occ=1→1 (stuck!)
[ROB_ALLOC] occ=1→1 (still stuck!)
Pipeline stalls after 2 instructions
Root Causes
// WRONG #1: Multi-driver conflict
always_comb begin
    alloc_ok = (occupancy < ROB_SIZE);  // ← Driver 1
end

always_ff @(posedge clk) begin
    if (reset)
        alloc_ok <= 1'b1;  // ← Driver 2 (CONFLICT!)
end

// WRONG #2: Hardcoded hack
if (reset)
    occupancy <= '0;
else
    occupancy <= 1;  // ← "Temporary" hack that stayed!

// WRONG #3: Update only when committing
if (commit_slots > 0) begin
    head <= (head + commit_slots) % ROB_SIZE;
    occupancy <= occupancy + alloc_count - commit_slots;  // ← Only here!
end
Fix
// CORRECT:
if (commit_slots > 0) begin
    head <= (head + commit_slots) % ROB_SIZE;
end
// ALWAYS update occupancy (outside commit conditional):
occupancy <= occupancy + alloc_count - commit_slots;
Lessons Learned
  • Never drive a signal from multiple always blocks (even if one is reset-only)
  • Occupancy = allocations - deallocations must update EVERY cycle
  • "Temporary" hacks become permanent bugs

Bug #3: LSU Load Index Truncation

Silent Index Truncation
12 hours wasted
Symptom
Cycle 34: Load from lq[9] completes, reads 'H' (0x48)
Cycle 35: CDB broadcasts tag=p0, value=0x00 (WRONG!)
Expected: tag=p57, value=0x48
Root Cause
// WRONG:
logic [3:0] load_in_flight_idx;  // ← Correct width (16 entries)

// But assignment truncates:
load_in_flight_idx <= lq_search_idx[2:0];  // ← TRUNCATES to 3 bits!

// What happened:
// lq[9] completes
// lq_search_idx = 9 (0b1001)
// Truncate to [2:0] = 0b001 = 1
// LSU broadcasts lq[1].dest_tag instead of lq[9].dest_tag
// lq[1] is stale, has tag=p0
// CDB broadcasts p0=0x00 instead of p57=0x48
Fix
// CORRECT:
load_in_flight_idx <= lq_search_idx;  // No truncation!
Lessons Learned
  • Array indices MUST match array size (16 entries = 4-bit index, not 3!)
  • Truncation bugs are silent (no compiler error, just wrong behavior)
  • Always check index width when debugging "value not broadcasting"

Bug #4: UART Not Receiving Characters

Overcomplicated Address Decoding
2 hours (solved by human frustration)
The AI Solution (Wrong)
// AI's overcomplicated version with address checking:
always_ff @(posedge clk) begin
    if (reset)
        tx_data_reg <= 8'h00;
    else if (write_en && (addr == ADDR_TX_DATA))
        tx_data_reg <= write_data[7:0];
end

// Tried 2 versions with different address decoding. Both failed.
The Human Solution (5 minutes)
// Human: "write_data has the characters, just display them."
always_ff @(posedge clk) begin
    if (reset)
        tx_data_reg <= 8'h00;
    else
        tx_data_reg <= write_data[7:0];  // No conditions!
end
Lesson Learned
AI overcomplicated with address checking and conditionals. Human recognized: "write_data has the characters, just display them." Direct signal probing beats complex logic. Sometimes the simplest solution is the right one.

§7 — Lessons from the Trenches

Technical Insights

Insight Why It Matters
Timing is everything Sequential logic must update in correct order. ROB occupancy updated inside commit conditional → never incremented during allocation → frozen at 1.
Index width matters Truncated indices cause silent corruption. 3-bit index for 16-entry array wraps at 8, broadcasting wrong tags.
Context is king LLMs give generic solutions; humans understand system state. AI suggested complex address decoding; human just probed the signal.
Test early, test often Bugs compound. Fix immediately or spend hours untangling cascading failures.

Design Patterns That Work

  • Round-robin allocation prevents starvation (free list, CDB arbiter)
  • Sequence numbers enforce ordering without stalling (LSU)
  • Separate allocation/commit enables speculation (ROB)
  • Tag broadcasting implements Tomasulo efficiently (CDB)

Debugging Skills

  • Read waveforms, not code: State machines fail in subtle ways only visible in traces
  • Isolate components: Test ROB alone before integrating with rename/dispatch
  • Print queue state: Dump LQ/SQ/IQ contents at critical cycles
  • Trust nothing: Even "working" modules may have latent bugs

The Real Achievement: Not just building an OOO CPU, but understanding it deeply enough to debug 73 hours of corner cases, explain every decision, and teach it to others. That's the difference between following a tutorial and actually knowing what you built.
