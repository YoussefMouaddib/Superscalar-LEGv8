§1 — The Three Core Structures

The rename stage wraps three distinct hardware structures. Each has a completely different job and a different timing model. Confusing them is the most common source of rename bugs.

free_list

A 64-bit bitmask. Tracks which physical registers in the rename pool (p32–p63) are available. Consulted every cycle to allocate fresh physical registers. Returns a physical register number per requesting lane.

rename_table

An array of 32 entries indexed by architectural register number. Each entry holds the physical register number of the most recent speculative write to that architectural register. Updated every cycle instructions are renamed.

committed_table (inside rename_table)

A shadow copy of the rename table that only moves forward when the ROB commits an instruction in order. On a flush, the speculative map_table reverts to committed_table. This is what makes precise exceptions possible.

The one-sentence mental model: the free list answers "which physical register can I use?", the rename table answers "which physical register holds the current value of architectural register Xn?", and the committed table answers "what is the last definitely-committed answer to that question?"

§2 — Free List: The Bitmask Allocator

The bitmask

The free list is a 64-bit register (free_mask). Bit i = 1 means physical register pi is available. Bit i = 0 means it is in use by an in-flight instruction.

On reset, bits 0–31 are cleared (these are the shadow registers — not allocatable) and bits 32–63 are set (the rename pool is fully empty). The allocation pointer alloc_ptr starts at 32 and walks round-robin through p32–p63 so that allocations spread across the pool and recently freed registers are not immediately reused.

Round-robin allocation algorithm

The allocator does not just take the first free bit from bit 32 — it walks from the last allocation pointer forward, wrapping within p32–p63. This prevents thrashing where the same registers cycle in and out immediately, giving freed registers time to "rest" before reuse.

Round-robin scan — combinational always_comb
// Always-comb: result must be available in the SAME cycle as alloc_en
always_comb begin
  automatic logic [63:0] temp_mask = free_mask;

  // Apply frees first (commit arrives same cycle, see note below)
  for (int j = 0; j < FREE_PORTS; j++) begin
    if (free_en[j]) temp_mask[free_phys[j]] = 1'b1;
  end

  search_ptr = alloc_ptr; // start from last pointer

  for (int a = 0; a < ALLOC_PORTS; a++) begin
    alloc_valid[a] = 1'b0; alloc_phys[a] = '0;
    if (alloc_en[a]) begin
      searches = 0;
      while (searches < 32) begin
        automatic int idx = 32 + ((search_ptr - 32) % 32);
        if (temp_mask[idx]) begin
          alloc_phys[a]  = idx;
          alloc_valid[a] = 1'b1;
          temp_mask[idx] = 1'b0; // mark tentatively used for port a+1
          search_ptr     = (idx + 1) % 64;
          break;
        end
        search_ptr = 32 + ((search_ptr - 32 + 1) % 32);
        searches++;
      end
    end
  end
end

Key subtlety: temp_mask is a local variable declared with automatic. Port 0's allocation clears its bit in temp_mask before port 1 searches, so two ports never claim the same register even when searching in the same cycle.

Sequential update

After the combinational block computes alloc_phys[] and alloc_valid[], the sequential block commits those choices on the clock edge: it writes the updated mask back to free_mask and advances alloc_ptr to the position just past the last successful allocation. The combinational block reads the registered alloc_ptr, not the just-computed next value — this is the normal read-registered-write pattern for any state machine in synchronous RTL.

§3 — Rename Table: Speculative & Committed Maps

Two tables, one module

Inside rename_table.sv there are two 32-entry arrays: map_table (speculative) and committed_table (architectural ground truth). They start identical — both hold an identity mapping where arch register i maps to physical register pi. They diverge as instructions are renamed, and they re-sync at commit.

The update rules

map_table update always_ff
// On clock edge, apply speculative renames
for (int j = 0; j < RENAME_PORTS; j++) begin
  if (rename_en[j] && arch_rd[j] != 5'd0) begin
    map_table[arch_rd[j]] <= new_phys_rd[j];
  end
end

Written every rename cycle. Reverts to committed_table on flush.

committed_table update always_ff
// On clock edge, advance committed state
for (int j = 0; j < COMMIT_PORTS; j++) begin
  if (commit_en[j] && commit_arch_rd[j] != 5'd0)
    begin
    committed_table[commit_arch_rd[j]]
      <= commit_phys_rd[j];
  end
end

Only moves on ROB commit. Never rolls back.

The critical invariant: committed_table[i] always holds the physical register that a program running in strict sequential order would have for arch register i. It is the "last known good" state. map_table[i] may be arbitrarily ahead of it — it reflects every unretired speculative write.

What commit does to the free list

When the ROB commits an instruction that wrote physical register pnew to architectural register Xn, the hardware must reclaim the physical register that previously held Xn's committed value. That old register is now dead — no instruction will ever read it again. The commit stage passes commit_phys_rd to the free list's free_en/free_phys ports. This is why the pool stays healthy: every commit allocates one slot and frees one slot in steady state.

§4 — Intra-Group Forwarding

The rename table is a sequential element — it only updates on the clock edge. But two instructions are renamed combinationally in the same cycle. If slot 0 writes X6 and slot 1 reads X6, the table still holds the old physical mapping for X6 when slot 1 does its lookup.

Without forwarding, slot 1 would be handed the wrong physical register. It would sit in the reservation station waiting for that register to become ready — but it never will, because the ADDI in slot 0 wrote a different physical register. The ROB deadlocks.

Forwarding logic — combinational override inside rename_table always_comb
always_comb begin
  for (int i = 0; i < LOOKUP_PORTS; i++) begin
    // Default: read from speculative map table
    phys_rs1[i] = (arch_rs1[i] == 5'd0) ? 6'd0 : map_table[arch_rs1[i]];
    phys_rs2[i] = (arch_rs2[i] == 5'd0) ? 6'd0 : map_table[arch_rs2[i]];

    // FORWARDING: check all earlier rename ports in same cycle
    for (int j = 0; j < RENAME_PORTS; j++) begin
      if (j < i && rename_en[j] && arch_rd[j] != 5'd0) begin
        if (arch_rs1[i] == arch_rd[j])
          phys_rs1[i] = new_phys_rd[j]; // forward just-allocated phys
        if (arch_rs2[i] == arch_rd[j])
          phys_rs2[i] = new_phys_rd[j];
      end
    end
  end
end

Why j < i? Only earlier slots can be producers for later slots within the same cycle. Slot 0 has no predecessor to forward from. Slot 1 checks slot 0. In a 4-wide design, slot 3 would check slots 0, 1, and 2.

How often does forwarding fire in hello_uart?

Every ADDI-STR pair in the string-building section triggers a forward. That is 16 consecutive cycles (cycles 6–22) where slot 0 writes X6 and slot 1 reads X6. The forwarding logic fires on every single one. Without it, the processor deadlocks on the very first STR in the program.

§5 — Combinational vs Sequential: The Key Split

This is the most important structural concept in the rename stage. Every operation falls into one of two categories and the rules are strict.

Combinational (always_comb)

Must produce its output in the same cycle as its inputs arrive. Results are available immediately to the pipeline stage that follows.

  • Free list search & allocation
  • Rename table read (rs1, rs2 lookup)
  • Intra-group forwarding override
  • alloc_en generation
Sequential (always_ff)

State elements. Updated on the rising clock edge. The new value is visible to combinational logic starting in the next cycle.

  • free_mask register
  • alloc_ptr register
  • map_table array
  • committed_table array
  • Pipeline output registers
Clock-cycle timing: what happens when, during cycle N

Classic bug: reading map_table in a sequential block. If you put the lookup inside always_ff, the result is delayed one cycle — slot 1 reads a mapping that is one cycle stale relative to when the decode inputs arrived. Everything processes with a one-cycle offset and your simulation shows garbage physical register assignments.

The separation also explains why forwarding must live in the combinational block. The forwarding logic reads new_phys_rd[j] — a value that was computed by the combinational free list search in the same cycle. Putting it in always_ff would mean "check if slot 0 wrote a register that slot 1 reads… in the cycle after we've already latched the wrong result." That is not forwarding, that is a bug.

§6 — Flush and Recovery

When the branch unit resolves a branch mispredict, it asserts flush_pipeline. The rename stage has a specific and ordered response.

Cycle
Signal
What happens

flush_pipeline=1
Branch unit sets flush. Asserted combinationally.
30
Pipeline regs
rename_valid <= '0 — all in-flight renamed outputs squashed. No new instructions enter the ROB this cycle.
30+

Reverts to committed_table snapshot. Any speculative renames since last commit are erased. This is the key recovery step — it restores the register mapping to a known-good state.
30+

Physical registers allocated to squashed instructions are returned. Because those instructions never committed, their commit_phys_rd was never sent to the free list — the reset logic returns them en masse.
31
Fetch
Redirected to correct branch target (0x00000098 = send_string). New instructions begin fetching.
33+
Normal
Rename stage processes new instructions from the correct path. map_table starts rebuilding from the committed snapshot.

Why precise exceptions work: The committed_table reflects only instructions that have retired in program order. Any instruction that was in-flight during the mispredict has not committed, so the committed table does not include its effects. Rolling map_table back to committed_table is equivalent to "undo every speculative write since the last in-order checkpoint" — exactly what precise exception semantics require.

§7 — SystemVerilog Notes

automatic variables in always_comb

The free list uses automatic variables inside its combinational block. This is required when you declare local variables inside an always_comb that must not retain state between evaluations.

automatic vs static in always_comb
// CORRECT — temp_mask is re-initialized every time the block re-evaluates
always_comb begin
  automatic logic [63:0] temp_mask = free_mask;
  automatic logic [5:0]  search_ptr = alloc_ptr;
  automatic int searches;
  // ... search logic modifying temp_mask ...
end

// WRONG — without automatic, temp_mask is a static variable.
// It retains its value from the PREVIOUS time the block ran.
// The allocation from last cycle bleeds into this cycle. Undefined behavior in simulation.
always_comb begin
  logic [63:0] temp_mask = free_mask; // BUG — static local
end

Non-blocking vs blocking assignments

The golden rule

always_ff: use <= (non-blocking) for all state updates. Multiple <= in the same block evaluate right-hand sides simultaneously from the current state, then all update together.

always_comb: use = (blocking) for local variable manipulation and output assignments. The result of one assignment is immediately visible to the next line in the block.

// always_ff: all <= evaluate before any take effect
always_ff @(posedge clk) begin
  free_mask <= updated_mask; // reads current free_mask, not updated_mask
  alloc_ptr <= new_alloc_ptr;
end

// always_comb: blocking = means sequential within the block
always_comb begin
  automatic logic [63:0] tmp = free_mask;
  tmp[alloc_phys[0]] = 1'b0; // immediately visible on next line
  if (tmp[33]) ...          // sees the cleared bit
end

Parameterized widths and array ports

// Multi-port arrays use packed dimensions:
input logic [FETCH_W-1:0][4:0] dec_rs1,  // FETCH_W lanes × 5 bits each
output logic [FETCH_W-1:0][5:0] alloc_phys, // FETCH_W lanes × 6 bits each

// Access lane i, bit field:
arch_rs1[i]    // 5-bit arch reg number for lane i
alloc_phys[i]  // 6-bit phys reg for lane i (0-63 needs 6 bits)

// The 6-bit width for physical registers: p0–p63 requires ceil(log2(64)) = 6 bits.
// Arch registers only need 5 bits (0-31). Mixing them without casting is a width bug.
phys_rs1[i] = 6'(arch_rs1[i]);  // explicit zero-extend to 6 bits

X0 special case

Physical register p0 is the hardwired-zero register. It maps to arch register X0 (XZR) and is never allocatable from the free list. The rename stage guards every allocation and lookup:

// Allocation: skip if destination is X0
alloc_en[i] = dec_valid[i] && dec_rd_valid[i]
            && (dec_rd[i] != 5'd0)   // ← guard
            && !flush_pipeline;

// Lookup: X0 always maps to p0
phys_rs1[i] = (arch_rs1[i] == 5'd0) ? 6'd0 : map_table[arch_rs1[i]];

// Pipeline register: X0 destination gets p0 and rd_valid=0
if (dec_rd[i] == 5'd0) begin
  rename_prd[i]      <= 6'd0;
  rename_rd_valid[i] <= 1'b0;
end

Why two separate modules (free_list and rename_table)?

Separation of concerns and independent testability. The free list has no knowledge of architectural registers — it just manages a pool of IDs. The rename table has no knowledge of availability — it only maps arch to phys. This makes unit-testing each independently in a testbench straightforward. If your rename produces wrong physical registers, you can narrow it to "free_list gave the wrong phys" vs "rename_table gave the wrong lookup" with separate waveforms.

§8 — Interview Cheatsheet

QuestionOne-paragraph answer
"Explain the free list" A 64-bit bitmask where bit i=1 means pi is available. On reset, bits 32–63 are set (rename pool), bits 0–31 clear (shadow registers, not allocatable). A round-robin pointer walks the pool starting from the last allocation so freshly freed registers cool down before reuse. The search is combinational — the result is available in the same cycle as alloc_en. The mask update is sequential — it commits on the clock edge. Freed registers come from the ROB commit path.
"What is the committed table and why is it separate?" committed_table is a shadow copy of the rename table that only updates when the ROB commits in order. map_table races ahead speculatively with every rename. On a branch mispredict or exception, rolling map_table back to committed_table restores the architectural state to the last in-order checkpoint — enabling precise exceptions without checkpointing the full register file.
"What is intra-group forwarding?" In a 2-wide superscalar, both slots are renamed in the same clock cycle. If slot 0 writes arch register X and slot 1 reads arch register X, the rename table has not yet been updated (that update is clocked, not combinational). Intra-group forwarding is a combinational bypass: before completing slot 1's lookup, check if any earlier slot in the same group is simultaneously renaming that register. If yes, override the table read with the just-allocated physical register. Without it, every ADDI-STR pair in hello_uart deadlocks.
"Why must the free list search be combinational?" Because the downstream pipeline stages (ROB, reservation station) need the physical register number in the same cycle the instruction passes through rename. If the search were sequential, the rename stage would need to stall for one cycle per instruction pair, halving throughput. The combinational search adds a logic path from free_mask and alloc_ptr to alloc_phys — this path must meet timing, which is why the search is bounded to 32 iterations (the pool size) and why the round-robin pointer avoids cold starts.
"What happens to the rename state on a flush?" rename_valid is cleared immediately (squashing in-flight outputs). On the next cycle, map_table is overwritten from committed_table. Physical registers that were allocated to squashed instructions are returned to the free list — because those instructions never committed, their commit_phys_rd was never asserted, so the free list must be cleaned up separately during flush recovery. Fetch redirects to the correct branch target and the pipeline restarts from a clean architectural state.
"How does the rename stage know it needs to stall?" It checks alloc_valid for each lane that requests an allocation. If the free list cannot satisfy a request (pool exhausted, which can happen if the ROB depth approaches the rename pool size), rename_ready is deasserted, backpressuring the decode stage. In steady-state operation the 32-slot pool is sized to match the 32-entry ROB, so stalls due to pool exhaustion should not occur in a correctly-sized design.
