§1 — Why the ROB Exists

An out-of-order processor executes instructions in whatever order their operands become available. That is where the performance comes from. But the programmer and the ISA expect results to appear as if everything ran in order. The ROB is the bridge between those two worlds.

The fundamental contract: Instructions may execute in any order. They must retire — become visible to the architectural state — in program order. The ROB enforces this contract.

Think of the ROB as a conveyor belt at airport security. You place your bag at one end (allocation). Your bag goes through the scanner in whatever order the machine processes it (out-of-order execution). But you can only collect your bag from the exit in the order it was placed on the belt (in-order commit). The belt does not care which bags finish first. The exit rule is strict.

Without the ROB, there is no way to answer: "If an exception occurs at instruction 7, what is the correct architectural state?" With the ROB, the answer is always: "Everything up through instruction 6 has committed. Nothing after that has touched the architectural register file."

What the ROB tracks

Every in-flight instruction from rename to commit — its architectural destination, physical register, PC, instruction type, and whether execution has completed (the ready bit).

What the ROB guarantees

Instructions write to the architectural register file only at commit time, in program order. Speculative results live only in physical registers. A flush can always undo any uncommitted work.

§2 — The ROB Entry Structure

Every instruction that passes through rename gets one ROB slot. The entry carries just enough information to know when the instruction is done, perform the architectural commit, support precise exceptions, and undo speculative work on a flush.

rob_entry_t packed struct packed struct
typedef struct packed {
  logic          valid;           // slot is occupied
  logic          ready;           // execution complete — eligible to commit
  logic [4:0]    arch_rd;          // architectural destination register (x0–x31)
  preg_tag_t     phys_rd;         // physical register holding the result
  logic          exception;       // execution raised a fault
  logic          is_store;        // store: commit triggers LSU retire to memory
  logic          is_load;         // load: set ready=1 at alloc
  logic          is_branch;       // branch: commit triggers predictor update
  logic [31:0]   pc;               // program counter (exceptions + predictor)
  logic          branch_taken;    // resolved outcome from branch execution unit
  logic [31:0]   branch_target;    // resolved target address
  logic          branch_is_call;  // BL — wrote X30
  logic          branch_is_return;// RET — consumed X30
} rob_entry_t;

The two fields that drive the entire commit engine are valid and ready. An entry is valid from the moment it is allocated. It becomes ready when an execution unit writes back via the CDB.

§3 — Phase 1: Allocation — Tail Advances

Every cycle, dispatch sends up to two instructions to the ROB via alloc_en. The ROB checks if there are enough free slots, assigns consecutive entries starting at the current tail, and returns the allocated indices. Those indices become the ROB tags that travel with each instruction through the RS and execution units.

Allocation — combinational index calculation always_comb
always_comb begin
  alloc_ok = 1'b0;
  free_slots = ROB_SIZE - occupancy;
  reqs = 0;
  for (k = 0; k < ISSUE_W; k++) if (alloc_en[k]) reqs++;
  if (reqs <= free_slots) begin
    alloc_ok = 1'b1;
    cur_tail = tail;              // read registered tail
    for (k = 0; k < ISSUE_W; k++) begin
      if (alloc_en[k]) begin
        alloc_idx[k] = cur_tail;  // return to dispatch same cycle
        cur_tail = (cur_tail + 1) % ROB_SIZE;
      end
    end
  end
end

The actual tail register and rob_mem[] entries are written in the sequential block. The combinational block only computes what the indices will be, so dispatch can forward them to the RS in the same cycle — the same comb/seq split as the rename stage's free list.

Why combinational index assignment? Dispatch needs to know the ROB tag before the sequential block fires, so it can write that tag into the RS entry in the same clock edge. A registered output would require an extra cycle, breaking the allocation handshake and stalling dispatch every single cycle.

§4 — Phase 2: Mark Ready — CDB Arrives

When an execution unit completes and broadcasts on the CDB, two things happen simultaneously: the RS wakes up dependent entries (Episode 4), and the ROB marks the relevant entry ready. There are two mark_ready ports — one per CDB lane — so both can fire in the same cycle.

Mark ready — sequential always_ff
if (mark_ready_en) begin
  if (rob_mem[mark_ready_idx].valid) begin   // guard: valid check
    if (mark_ready_val)  rob_mem[mark_ready_idx].ready     <= 1'b1;
    if (mark_exception)  rob_mem[mark_ready_idx].exception  <= 1'b1;
  end
end
// Port 1 — symmetric, same logic

The valid guard prevents a stale CDB signal (from an entry flushed during a mispredict) from corrupting a freshly reallocated slot at the same index.

§5 — Phase 3: In-Order Commit — Head Advances

Commit is the most constrained phase. Every cycle, the ROB scans from the head forward and commits up to two entries — but only consecutive ready entries starting from the head. If the head entry is not ready, nothing commits. The head can never skip a not-ready entry.

Commit scan — sequential always_ff
commit_slots = 0;
look_idx = head;
for (j = 0; j < ISSUE_W; j++) begin
  if (occupancy > 0
      && rob_mem[look_idx].valid
      && rob_mem[look_idx].ready) begin
    commit_valid[j]   <= 1'b1;
    commit_arch_rd[j] <= rob_mem[look_idx].arch_rd;
    commit_phys_rd[j] <= rob_mem[look_idx].phys_rd;
    // ... store / branch / load metadata ...
    rob_mem[look_idx].valid <= 1'b0;  // free the slot
    rob_mem[look_idx].ready <= 1'b0;
    look_idx = (look_idx + 1) % ROB_SIZE;
    commit_slots++;
  end else begin
    break;  // stop at first non-ready — enforces in-order retirement
  end
end
if (commit_slots > 0)
  head <= (head + commit_slots) % ROB_SIZE;
occupancy <= occupancy + alloc_count - commit_slots;

The break enforces in-order retirement. Without it, the loop would skip not-ready entries and commit out of order, violating precise exception semantics and corrupting the branch predictor update sequence.

§6 — The Circular FIFO: Head, Tail, Occupancy

The ROB is a circular buffer with 32 slots indexed 0–31. Three state variables govern it: head (oldest, commits from here), tail (next empty, allocations enter here), and occupancy. When tail reaches 31, it wraps back to 0 — the same slots that head will eventually reach after 32 commits.

Wrap example from the simulation: At cycle 19, the ROB allocates ROB[0] and ROB[1] — tail has wrapped from 31 back to 0. Head is at 15. Occupancy = 17. Old slots at indices 0–14 are free (they committed) and are being reused for new instructions.

head

Points to the oldest uncommitted instruction. Advances by commit_slots per cycle, wrapping mod 32. Only this slot can commit. Everything behind head has already retired.

tail

Points to the next free slot. Advances by alloc_count per cycle. The combinational block reads the current registered tail to produce alloc_idx[] before the sequential update moves it forward.

§8 — Branch Misprediction and Partial Flush

At cycle 30, the branch unit resolves the B send_string at PC 0xC0 as taken-to-0x98 with mispredict=1. The processor has been speculatively fetching past 0xC0 for several cycles. The flush must undo that speculative work while preserving correctly-executing instructions already in the ROB.

Selective flush, not full wipe: Unlike the RS (which wipes everything in one edge), the ROB performs a partial flush. Only entries after the mispredicting branch are invalidated. Entries from head up to the branch are preserved — they are on the correct path and should still retire. This avoids re-fetching and re-executing correct work.

Partial flush logic always_ff
if (flush_pipeline) begin
  // Walk from flush_rob_idx+1 to current tail — invalidate speculative entries
  automatic int idx = (flush_rob_idx + 1) % ROB_SIZE;
  automatic int count = 0;
  while (idx != tail && count < ROB_SIZE) begin
    rob_mem[idx].valid <= 1'b0;
    rob_mem[idx].ready <= 1'b0;
    idx = (idx + 1) % ROB_SIZE;
    count++;
  end
  // Snap tail back to just after the branch
  tail <= (flush_rob_idx + 1) % ROB_SIZE;
  occupancy <= /* entries from head to flush_rob_idx */;
end

After the flush, tail is repositioned so correct-path instructions start filling the ROB immediately from cycle 31 onward.

§9 — Stores, Loads, and ready=1 at Allocation

Store instructions do not produce a register result — their architectural effect is a memory write. Memory writes must happen in program order. The ROB handles this with one rule: stores are allocated with ready=1.

// At allocation: stores and loads start as ready
rob_mem[cur_tail].ready <= alloc_is_store[k] | alloc_is_load[k];

The LSU has already accepted the store into its store buffer at dispatch time. From the ROB's perspective, the store is "done" immediately — there is nothing to wait for. The only reason a store stays in the ROB at all is to ensure the actual memory write fires in program order at commit time, not speculatively ahead of older instructions.

Looking at the simulation: ROB entry 9 at PC 0x24 (the first STR X6,[X9,#0]) shows R=1 as early as cycle 8, before most ALU instructions have produced their CDB results. Every STR visible in the table from cycle 10 onward has R=1 immediately — that is why the alternating ADDI+STR pairs in cycles 14–20 always commit as a smooth pair rather than waiting on the store to "finish."

Loads are also ready=1 at allocation in this implementation. The load data comes back from memory and updates the physical register via CDB — but the ROB's commit role for a load is only "this instruction happened at this PC in order." By the time a load reaches the ROB head, the data has already been delivered. Ready=1 at alloc is correct here too.

§10 — SystemVerilog Notes

Combinational/sequential split — the same pattern again

Like the free list in rename and the RS allocation, the ROB uses a combinational block to compute allocation indices (so dispatch receives them in the same cycle) and a sequential block to write rob_mem[] and update tail. The combinational block reads the registered tail — this is correct because the registered tail reflects state before this cycle's allocations, which is exactly what is needed to compute this cycle's indices.

Occupancy is a single atomic expression

occupancy <= occupancy + alloc_count - commit_slots;

Both allocation and commit happen in the same sequential block. alloc_count and commit_slots are local automatic variables accumulated within the block. The final occupancy is written once at the end — no intermediate state, no race between allocation and commit.

The break in the commit loop is a correctness requirement

The commit for-loop iterates up to ISSUE_W=2 times. The break on encountering a non-ready entry enforces in-order retirement. Without it, the loop would skip the not-ready entry and commit the next one — out-of-order commit. The ARF would receive writes in the wrong order, exception recovery would produce corrupted state, and the branch predictor would train on the wrong instruction order.

The valid guard on mark_ready

After a flush, entries are invalidated. A CDB broadcast in-flight during the flush might arrive one cycle late and try to mark-ready a slot that was just cleared and possibly reallocated to a different new instruction. The rob_mem[idx].valid guard prevents the new instruction from being incorrectly marked ready by a stale CDB signal from the flushed instruction.

§11 — Interview Cheatsheet

What is the ROB and why does every OOO processor need one?

The Reorder Buffer is a circular FIFO that tracks every in-flight instruction from rename to commit. Instructions are allocated at the tail in program order and retired at the head in program order, even though execution happens out of order between those two points. Without the ROB, there is no mechanism to ensure architectural state — register file contents, memory write ordering, exception behavior — matches what a sequential execution would have produced. The ROB is what allows the processor to say: everything before this point is architecturally committed; everything after can be undone.

What is precise exception support and how does the ROB provide it?

A precise exception means that when a fault fires, the architectural state reflects exactly the sequential execution up to but not including the faulting instruction — no more, no less. The ROB provides this because instructions only write to the architectural register file at commit time, in program order. If instruction 7 faults, everything before it has already committed (state is clean and consistent), and everything from 7 onward has not committed (those results are still only in physical registers). The flush discards everything from 7 onward. The OS exception handler sees a consistent, recoverable state.

Why can the commit queue only advance from the head? Why not skip a not-ready entry?

Skipping would violate in-order commit. If instruction 4 commits before instruction 3, instruction 4's result becomes architectural first. Now if instruction 3 raises an exception, the architectural state already includes instruction 4's writes — which a strictly sequential execution would never have seen. The handler sees corrupted state. More practically, the branch predictor update from instruction 4's commit could redirect fetch to the wrong path before instruction 3's outcome is even known. The break in the commit loop is a correctness requirement, not an optimization.

Why are stores allocated with ready=1 in the ROB?

A store's result is a memory write, not a register write. The LSU accepts the store into its store buffer immediately at dispatch — the address and data have been computed. From the ROB's perspective, the store's computation is done. The ROB's role for a store is only to ensure the memory write fires in program order at commit time, not speculatively. Since there is nothing for the ROB to "wait for" in terms of register production, setting ready=1 at allocation means stores never block the commit head, keeping the pipeline from stalling unnecessarily on back-to-back stores.

What is the difference between the ROB flush and the RS flush?

The RS does a complete wipe — all 32 entries invalidated in one clock edge, because the RS has no ordering information about which entries were fetched before or after the mispredicting branch. The ROB does a selective partial flush — only entries after the mispredicting branch's ROB index are invalidated. Entries from head up to and including the branch are preserved because they are on the correct path. After the ROB flush, tail snaps back to just after the branch, and new correct-path instructions fill in from cycle 31 onward without needing to re-execute work that was already committed or is still correctly in-flight.

What is the relationship between ROB size and rename pool size?

The rename pool must be at least as large as the ROB. Every in-flight instruction that has a destination register holds one physical register from the rename pool. The maximum number of such instructions in-flight simultaneously is bounded by the ROB size. If the rename pool were smaller than the ROB, the processor would run out of physical registers before the ROB filled up, causing spurious dispatch stalls. In this implementation, both are sized at 32: ROB holds 32 entries and the rename pool is p32–p63 — a 1:1 sizing ensuring the rename stage never starves before the ROB fills.
