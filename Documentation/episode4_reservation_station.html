§1 — What Dispatch Does and Why It Exists

Dispatch sits between rename and the execution units. Its job is to take physically-renamed instructions and hand them off to the correct execution resource — either the Reservation Station (for ALU/branch work) or the Load-Store Unit — along with operand values and readiness information. It also maintains the scoreboard, a fast lookup of which physical registers are currently "in-flight" (written but not yet produced).

What dispatch sends to RS

Each allocated RS entry gets: physical destination tag, two physical source tags, current values of those sources (from PRF), readiness bits for each source, the opcode, the ROB tag, PC, and immediate. The RS is a holding buffer — it keeps the instruction until both operands are ready.

What dispatch sends to LSU

Load/store instructions bypass the RS entirely and go directly to the LSU queue. They still get the same operand readiness treatment (scoreboard + CDB bypass + PRF read), but they have their own dedicated hardware path.

The pipeline position: Rename → Dispatch → [RS / LSU] → Execute → CDB → RS wakeup → Issue → Execute again (no, that's not a loop — issue from RS to execute, then result on CDB wakes up any RS entries waiting for it).

§2 — The RS Entry Structure

Each of the 32 RS entries is a packed struct. Understanding what each field does is essential before the algorithms make sense.

rs_entry_t struct packed struct
typedef struct packed {
    logic          valid;       // 1 = this slot is occupied
    logic [5:0]    dst_tag;     // physical destination register
    logic [5:0]    src1_tag;    // physical source 1 tag (for CDB matching)
    logic [5:0]    src2_tag;    // physical source 2 tag
    logic [31:0]   src1_val;    // value of src1 (valid when src1_ready)
    logic [31:0]   src2_val;    // value of src2 (valid when src2_ready)
    logic          src1_ready;  // 1 = src1_val is the correct final value
    logic          src2_ready;  // 1 = src2_val is the correct final value
    logic [11:0]   opcode;      // {rename_opcode[5:0], alu_func[5:0]}
    logic [5:0]    rob_tag;     // ROB index — used for clearing after issue
    logic [4:0]    age;         // cycles spent in RS, drives oldest-first select
    logic [31:0]   pc;          // PC for branch resolution
    logic [31:0]   imm;         // immediate value
} rs_entry_t;

The age field starts at 0 when the entry is allocated and increments every cycle the entry stays in the RS. The issue selector picks the oldest ready entry — highest age wins. This prevents starvation and respects program order among independent ready instructions.

§3 — Dispatch: Scoreboard, PRF Read, and Operand Readiness

The scoreboard

The scoreboard is a 64-bit register (preg_ready) — one bit per physical register. Bit i = 1 means pi's value is valid and can be read directly from the PRF. Bit i = 0 means an in-flight instruction will write pi and its value is not yet available.

Mark busy on alloc always_ff
for (int i = 0; i < FETCH_W; i++) begin
  if (rob_alloc_en[i] && rob_alloc_ok
      && rename_rd_valid[i]) begin
    preg_ready[rename_prd[i]] <= 1'b0;
  end
end

When a new instruction is dispatched and has a destination register, that register is immediately marked busy — even before the instruction executes.

Mark ready on CDB always_ff
for (int j = 0; j < 2; j++) begin
  if (cdb_valid[j]) begin
    preg_ready[cdb_tag[j]] <= 1'b1;
  end
end

When an execution unit broadcasts its result on the CDB, the scoreboard marks that register ready. Future dispatches can read it directly from the PRF.

PRF read ports and operand readiness check

Dispatch has four PRF read ports: instruction 0 uses ports 0 and 1, instruction 1 uses ports 2 and 3. For each source operand, readiness is determined in priority order:

  1. No source needed (rs_valid=0): source is trivially ready, value is 0 or the immediate.

  2. Source is p0 (XZR): always ready, always 0.

  3. CDB bypass: if a CDB broadcast is happening this cycle with a matching tag, use that value — the PRF hasn't been written yet but the result is available on the wire.

  4. Scoreboard check: preg_ready[prs] — if set, read the value from the PRF. If not set, mark source as not ready and store only the tag (the RS will wait for the CDB to supply the value later).

  5. Same-cycle dependency: if slot 0 writes a register that slot 1 reads, the scoreboard hasn't been updated yet. Force src_ready=0 for slot 1 regardless of scoreboard state.

Same-cycle dependency vs intra-group forwarding: In the rename stage, forwarding ensures slot 1 gets the correct physical register tag when slot 0 renames a register. In dispatch, the same-cycle dependency check forces src_ready=0 because the PRF has not yet been written. The RS entry will be woken up when the CDB fires. They solve different parts of the same problem — rename fixes which physical register; dispatch fixes whether the value is available yet.

§4 — The Five-Step Sequential Algorithm

The RS's always_ff block executes five ordered steps every cycle. The ordering matters: later steps can see the effects of earlier steps within the same clock edge (because they all operate on the same local variables before the final <= assignments commit).

Five-step RS sequential logic overview always_ff

  1. Register issue outputs. Latch the combinational issue selection (issue_valid_comb, etc.) into the registered output ports. These are what the execution units read next cycle.

  2. Clear entries issued last cycle. Look at issue_valid (last cycle's registered value) and issued_rob_tag_reg (captured ROB tags). Find matching RS entries by ROB tag and set their valid=0. This frees the slot one cycle after issue.

  3. Compute free slots. Build free_slots bitmask: a slot is free if !valid or if it was just cleared in step 2.

  4. Allocate new entries. Walk through incoming alloc_en[] lanes and assign each to the next available free slot, filling in all struct fields. age starts at 0.

  5. CDB wakeup + age increment. For every valid, non-cleared entry: check both CDB ports for tag matches on src1 and src2. If matched, capture the CDB value and set the ready bit. Increment age unconditionally for all valid entries.

Why step 2 uses last cycle's issue output, not this cycle's combinational selection: The combinational selection (issue_valid_comb) picks the entries to issue this cycle. But those entries can't be cleared until the execution unit has actually consumed them — and the execution unit reads the registered outputs (step 1). So the slot is cleared one cycle after the combinational select fires. The issued_rob_tag_reg register captures which ROB tag was selected so step 2 can find the right entry to clear.

  • Issue selection scan (oldest ready)
  • Operand readiness check
  • PRF read port mux

§5 — Issue Selection: Oldest-First, 2-Wide

Every cycle, the combinational block scans all 32 RS entries and selects up to 2 that are ready to issue — both source operands ready — choosing the oldest (highest age) among eligible entries. The two ports are selected independently with a considered_entries bitmask preventing double-selection.

Oldest-first issue selection always_comb
for (int p = 0; p < ISSUE_W; p++) begin
  for (int i = 0; i < RS_ENTRIES; i++) begin
    if (rs_mem[i].valid
        && rs_mem[i].src1_ready
        && rs_mem[i].src2_ready
        && !considered_entries[i]) begin

      if (!issue_valid_comb[p]
          || rs_mem[i].age > oldest[p].age) begin
        oldest[p] = rs_mem[i];     // new best candidate
        oldest_idx[p] = i;
        issue_valid_comb[p] = 1'b1;
      end
    end
  end
  if (issue_valid_comb[p] && oldest_idx[p] != -1)
    considered_entries[oldest_idx[p]] = 1'b1; // block from port 1
end

Port 0 always gets the oldest ready entry. Port 1 gets the oldest ready entry excluding whichever entry port 0 selected. Both operate on the pre-wakeup state — CDB values applied this cycle are visible to next cycle's issue scan.

Age counter simulation — cycle 10 RS snapshot

Bar height = age value. All five entries at cycle 10 have both sources ready. The issue selector picks the two with the highest age: entry 3 (age=5) and entry 0 (age=2) win in that cycle.

Why oldest-first? Age-based selection approximates program order among ready instructions. Without it, a younger instruction could issue repeatedly while an older one starves, violating the assumption that the ROB can commit in order. Age doesn't guarantee in-order execution — the OOO core deliberately violates that — but it prevents pathological starvation.

§6 — CDB Wakeup and Value Capture

When an execution unit completes, it broadcasts a (tag, value) pair on the Common Data Bus. Step 5 of the sequential algorithm scans every valid RS entry and checks both source tags against both CDB ports. A match causes two simultaneous writes: the value is captured into src_val and the ready bit is set to 1. The entry can then be selected by the combinational issue logic in the very next cycle.

Cycle 7 CDB wakeup — CDB0: p32=0x1, CDB1: p33=0x10
CDB0 fires: tag=p32   value=0x00000001
CDB1 fires: tag=p33   value=0x00000010
Entry 2 dst=p34 src1=p32 ✓ match CDB0 → ready, val=1 src2=p33 ✓ match CDB1 → ready, val=16 → both ready! eligible next cycle
Entry 3 dst=p35 src1=p34 — no match src2=p0(ready) → still waiting for p34

Confirmed by log: [CDB0] tag=p32 value=00000001 and [CDB1] tag=p33 value=00000010 at cycle 6, and entry 2 issues at cycle 8.

CDB vs PRF: The CDB is a broadcast wire — every RS entry listens simultaneously. The PRF is a register file — it can only be read with a limited number of read ports. Capturing values from the CDB into RS entries avoids adding more PRF read ports and keeps the operand path latency-free: by the time an entry is selected for issue, its values are already sitting inside the RS entry itself.

§8 — Flush and Recovery

On flush_pipeline assertion (branch mispredict), the RS takes a single-cycle action: all 32 entries are invalidated and the registered issue outputs are cleared. The RS is fully empty one cycle after flush — no drain, no partial squash.

The simulation log confirms: RS entries 0, 2, 5 (which held speculative-path instructions) are still present at cycle 31–33 because they were allocated before the flush resolved, but no new allocations enter the RS during flush.

Why entries linger after flush (cycles 31–40): The log shows entries p59, p0 (ROB 10), p0 (ROB 13) sitting in the RS with age growing to 14+ and never issuing. These are the load and branch instructions that were waiting for p57 (the loaded value from scratchpad) and p58 (SUB result). Their operand p57 was never produced — the load at ROB 9 was waiting for the LSU to resolve. This is the long-latency load stall visible in the simulation. The RS doesn't flush these because they were allocated before the mispredict but haven't issued yet — they represent real work on the correct path that must eventually complete.

§9 — SystemVerilog Notes

The 1-cycle issue latency: why outputs are registered

The issue outputs (issue_valid, issue_src1_val, etc.) are registered — they go through an always_ff in step 1. The combinational selection happens this cycle; the execution unit reads the registered value next cycle. This adds one cycle of latency to issue but makes timing closure easier — the wide 32-entry scan doesn't have to meet the same clock as the execution unit's input setup time.

// Step 1: register combinational selection → execution unit reads next cycle
issue_valid     <= issue_valid_comb;
issue_src1_val  <= issue_src1_val_comb;
// ... all other issue fields ...

// Capture ROB tag so step 2 knows what to clear NEXT cycle
for (int p = 0; p < ISSUE_W; p++) begin
  if (issue_valid_comb[p])
    issued_rob_tag_reg[p] <= issue_rob_tag_comb[p];
end

Clear-mask before free-slot calculation

Steps 2 and 3 must be ordered carefully. Step 2 builds clear_mask — the set of entries being freed this cycle. Step 3 then computes free_slots = !valid || clear_mask. This allows step 4 (allocation) to immediately reuse the slots that were just cleared in the same clock edge — one cycle reuse rather than two. If step 3 used only !valid, a cleared slot would appear occupied for one extra cycle.

// Step 2: build clear mask from LAST cycle's issued rob tags
for (int p = 0; p < ISSUE_W; p++) begin
  if (issue_valid[p]) begin  // registered = last cycle
    for (int i = 0; i < RS_ENTRIES; i++) begin
      if (rs_mem[i].valid
          && rs_mem[i].rob_tag == issued_rob_tag_reg[p])
        clear_mask[i] = 1'b1;
    end
  end
end

// Step 3: free_slots includes just-cleared entries
for (int i = 0; i < RS_ENTRIES; i++)
  free_slots[i] = !rs_mem[i].valid || clear_mask[i];

automatic variables in always_ff

The RS sequential block uses automatic local variables (free_slots, clear_mask, current_slot) even though it's an always_ff. This is necessary because these locals are used as scratch variables within the block — they should not retain values between clock edges. Without automatic, a simulator would treat them as static, carrying over stale values and causing incorrect slot allocation.

dispatch_stall composition

dispatch_stall = rs_full || !rob_alloc_ok || flush_pipeline || memory_op_stall;

// memory_op_stall: can only dispatch 1 memory op per cycle (LSU is 1-wide)
// if both rename lanes have a load/store, stall the second one
automatic int mem_op_count = 0;
for (int i = 0; i < FETCH_W; i++) begin
  if (rename_valid[i] && (rename_is_load[i] || rename_is_store[i]))
    mem_op_count++;
end
memory_op_stall = (mem_op_count > 1);

LSU base address caching

The dispatch module caches the last-dispatched LSU base tag and value (cached_base_tag, cached_base_value). In hello_uart's store loop, every STR X6, [X9, #N] uses X9 as the base — and X9 maps to p39 for the entire string section. Rather than re-reading the PRF every cycle for the same tag, the cache detects the repeated tag and supplies the stored value directly. This saves a PRF read port conflict on hot loops.

§10 — Interview Cheatsheet

What is a Reservation Station and why do we need it?

A Reservation Station is a buffer that holds instructions after they have been renamed but before their source operands are ready. In an in-order machine, an instruction with a not-yet-produced operand would stall the whole pipeline. The RS instead parks the instruction, continues accepting newer instructions, and wakes up the parked instruction the moment the CDB broadcasts the missing value. This decouples the issue rate from data dependencies — the processor can keep issuing independent instructions while a long-latency operation (like a cache miss) is in flight.

What are the five steps in the RS's sequential block and why are they ordered that way?

Step 1 registers the combinational issue outputs so execution units see stable inputs. Step 2 clears the entries that were issued last cycle (using the captured ROB tags) — not this cycle's selection, because the execution unit only just received those outputs. Step 3 computes free slots including just-cleared ones, allowing immediate reuse. Step 4 allocates new entries from dispatch into those free slots. Step 5 applies CDB wakeup values and increments age counters. The ordering ensures no slot is double-allocated, clearing always precedes filling, and wakeup happens on fresh entries too.

Why oldest-first selection? Couldn't you just pick any ready entry?

You could, and the machine would still be correct — the ROB enforces in-order commit regardless of issue order. But picking any ready entry risks starvation: an entry that has been waiting a long time could be bypassed indefinitely by younger entries that happen to always be ready. Oldest-first selection (maximum age) guarantees bounded waiting time and approximates program order among independent instructions, which tends to reduce ROB occupancy by committing early instructions sooner.

What is the scoreboard in dispatch, and how does it differ from the RS readiness bits?

The scoreboard in dispatch is a per-physical-register ready bit maintained in the dispatch stage. It answers "has this register's value been committed to the PRF?" If yes, dispatch can read the value from the PRF and mark the RS entry's source as immediately ready. If no, dispatch stores only the tag and marks the source not ready — the RS will wait for the CDB. The RS readiness bits are per-entry state that gets updated by CDB wakeup. They're different levels of the same concept: the scoreboard is the global view; the RS readiness bit is the per-entry local view captured at allocation time and updated on CDB match.

Why does dispatch check for same-cycle dependencies separately from the scoreboard?

The scoreboard is a registered value — it reflects state committed at the previous clock edge. When two instructions are dispatched in the same cycle (2-wide) and slot 0 writes a register that slot 1 reads, that new busy mark hasn't propagated to the scoreboard yet (it will on the next clock edge). Without the explicit same-cycle check, slot 1 would read the scoreboard as "ready" and dispatch with src_ready=1 — but the value doesn't exist yet. The same-cycle check forces src_ready=0 in this case, ensuring the RS entry waits for the CDB broadcast from slot 0's execution.

Why do some RS entries in cycles 31–40 have age=10+ but never issue?

These entries are waiting for p57 — the result of a load instruction (ROB 9, PC 0xa4: LDR X4, [X3, #0]). The load reads from scratchpad address 0x00002000 and is the critical-path operation that feeds the branch condition and the ADD+CBNZ send loop. The load itself depends on p56 (the result of ADDI X3, X9, #0) and p38 (0x0000000c, the UART status mask). Once p57 is produced, entries p59 (the AND), p0/ROB10 (the CBZ), and p0/ROB13 (the CBNZ) all become eligible. The long wait reflects the realistic latency of the load-use chain in the send loop — this is the structural reason why the UART output stalls for several cycles between characters.
